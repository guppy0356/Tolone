# 依存パッケージ更新プロセスの実行

仕様は [process.md](process.md) にある。用語、前提、判断の早見表、§1〜§8 がすべてそこにある。

**以下の道順は索引であって規則ではない。** どの節へ行くかを示すだけで、合格条件も、値の規則も、禁止操作も持っていない。各段を実行する前に process.md の該当節を読み、判断はその本文に従う。道順の圧縮された表現を規則として使わない。

## このリポジトリでの束縛

process.md のプレースホルダをこのリポジトリの値に読み替える。

- `<apps>` = `playgrounds`
- 「アプリ」= `playgrounds/*` の 13 個。`packages/tailwind` とルートはアプリではない（前提の「各アプリは自分の typecheck / test / build を持つ」に当たらない）。ただし `pnpm update -r` はルートの package.json の直書きも更新し、それは §6 の 8. が扱う
- 「Issue」= GitHub Issue。`gh` で作成・検索・close する

## 実行主体

この Skill を起動した実行は「人が実行する」に当たる。process.md はこの区分を定めていない（仕様上の不足）。この Skill ではこう扱うと決めた。

process.md 中の「自動実行は〜」「自動実行なら〜」で始まる分岐は適用しない。§1 の中断条件、§2 の 5. の draft PR で終了、§3 を代表名の昇順で最初の 1 候補までとする制限、解除を行わないこと、はいずれもこの実行には当たらない。

process.md が「人が行う」と書いている箇所では判定せずに止まり、材料（不合格アプリ、失敗内容、新しい `unmet peer` 行、候補の版）を示して利用者に判定を求める。答えを受けてから先へ進む。

## 道順

上から順に。1 つの PR を merge してから次へ進む。

### 0. はじめる前に、そろっているか見る — §1

process.md の §1 を読み、確認表の全行を実行する。

- 合格条件を満たさない行は「満たさないとき」の列に従う
- ベースラインが落ちたアプリは Issue に書いて今回の検証から外し、**更新は始める**
- 候補一覧が `ERR_PNPM_NO_MATCHING_VERSION` で取れないときは Issue に書いて**待つ。更新を始めない**
- 候補の区分（範囲内更新 / メジャー更新）と組の判定を §1 の規則で行う
- 「スクリプト」の行で追加が要るとき、追加するスクリプトの中身は process.md に定義が無い（仕様上の不足）。中身を利用者に確認してから追加する

### 1. 範囲の中で上がるぶんを全部いっしょに上げる — §2

ブランチ `deps/range/<YYYY-MM-DD>`。process.md の §2 を読む。

`pnpm update -r` を 1 回 → §2 の 3. の 3 条件で検査 → §6 の検証を全アプリ → 全アプリ合格なら 1 コミットで終わり。

落ちたら §2 の 5. に従い、全部戻して 1 パッケージずつやり直す。

### 2. メジャー更新を 1 パッケージずつ — §3

§2 の PR を merge してから始める。ブランチ `deps/major/<pkg>-<version>`。候補は代表名の昇順で 1 つずつ、前の PR を merge してから次へ。process.md の §3 を読む。

対象アプリを全部 `latest` に上げてみる → §6 の検証を全アプリ → §3 の 4. の表で分類する。

不合格アプリがあれば §3 の 5. の判定へ。**この判定は人が行う。**

### 3. 追いつけないアプリを置いていく — §4

§2、§3、§5、または §1 の「lockfile の整合」で「置いていく」と判定したアプリがある状態から始める。process.md の §4 の原則と手順 1.〜7. に従う。

共有 catalog は新版のまま、置いていくアプリの package.json だけ置いていく直書きにする。値の 2 形式とどちらを書くかは §4 の 2. にある。共有 catalog の変更と package.json の変更は同じ 1 コミットに入れる。

### 4. 追いつけるようになったアプリを戻す — §4 の「解除」

そのラウンドの §2 と §3 の PR をすべて merge した後に、単独の PR で行う。ブランチ `deps/unblock/<YYYY-MM-DD>`。process.md の §4 の「解除」1.〜4. に従う。解除の中で依存を上げない。

## 人が止まる 6 か所

process.md が「人が行う」と名指ししている箇所。ここでは判定せず、材料を示して利用者に問う。

| 箇所 | 何を問うか |
|---|---|
| §3 の 5. | 落ちたアプリを直すか、置いていくか |
| §4 の 5. | 警告に出ない落ち方のとき、原因のパッケージはどれか |
| §6 の 9. | peer 警告を `peerDependencyRules.allowedVersions` に書くか |
| §3 の 6. | 脆弱性対応で `minimumReleaseAgeExclude` に版を書くか |
| §1 | `unblock:` 行が無い Issue を解除してよいか |
| 全体 | PR を merge する |

## 落ちたら、どこへ戻るか

| 落ちた場所 | 戻る先 | そのあと |
|---|---|---|
| 0 ベースライン | 戻らない | そのアプリを検証から外して、更新は始める |
| 0 候補一覧 | 止まる | 版が育つまで待つ。更新を始めない |
| 1 一括更新 | 1 の頭 | 全部戻して 1 パッケージずつやり直す |
| 1 一部のアプリだけ | 2 の「人」 | 直すか置いていくかを判定する |
| 2 全アプリ | 見送り | Issue に書く。次回また候補に出る |
| 2 一部のアプリだけ | 3 | そのアプリだけ置いていく |
| 3 置いていった後 | 3 の `pnpm install` | 原因のパッケージを足してやり直す |
| 4 戻した後 | 2 の「人」 | 戻しを取り消して再判定。それでも落ちたら PR を close |
| 検証の 1 回目 | 同じコマンド | もう 1 回だけ。2 回目も落ちたら不合格 |

## 関門（§6）

0〜4 に出てくる「検証」はいつも同じ 9 項目。合格条件は process.md の §6 の表にある。対象は全アプリで、変更のあったアプリだけに絞らない。

1. `pnpm dedupe --check`
2. `pnpm install --frozen-lockfile`
3. `pnpm-workspace.yaml` の差分
4. peer 警告
5. `pnpm ls -r <pkg> --depth 0 --json`
6. `pnpm -r --if-present run generate`
7. アプリごとに `typecheck`、`test`、`build`
8. ルートの依存
9. peer 警告の記入（**人**）

## やってはいけない操作

process.md の §7 の表にある。手順のコマンドを打つ前に §7 を読む。
