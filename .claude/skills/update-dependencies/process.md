# 依存パッケージ更新プロセス

pnpm workspace に複数の独立したアプリがある monorepo を対象にする。
各アプリは自分の typecheck / test / build を持つ。
この文書は「pnpm で何ができるか」ではなく「この状況ではこうする」を定める。
人が判断する箇所は「人が判断する」と明記する。それ以外はコマンドと合否条件で決まる。

## 用語

- 共有 catalog: `pnpm-workspace.yaml` の `catalog:`。pnpm の用語では default catalog。package.json からは `"catalog:"` で参照する。
- named catalog: `pnpm-workspace.yaml` の `catalogs: <名前>:`。この文書では使わない。理由は §5 に書く。
- 直書き: package.json に `"^1.2.3"` のように範囲を直接書くこと。
- 範囲内更新: 今の範囲を満たす最新版へ上げること。`pnpm update` の既定動作。
- メジャー更新: 今の範囲を超えて上げること。`pnpm update --latest` か、範囲の書き換えで起きる。
- 置いていく: 一部のアプリだけを旧版に留めること。
- 置いていく直書き: 共有 catalog にあるパッケージを、置いていくアプリの package.json に `"catalog:"` の代わりに直接書いた範囲。値は次の 2 形式に限る。旧メジャーに留めるなら `^<旧メジャーの版>`。範囲内更新で壊れた版を避けるなら `x.y.z` の固定版。
- 前進するアプリ / 置いていくアプリ: ある更新で新版に進むアプリ / 置いていく直書きで旧版に留めるアプリ。
- 候補一覧: アプリごとに `pnpm --filter <app> outdated --format json` と `pnpm --filter <app> outdated --compatible --format json` の 2 つを実行し、アプリ名を付けて連結した一覧。どちらかの実行に現れたパッケージを 1 行とする。行は 3 つの版を持つ。`current` は今の解決版。`latest` は `--compatible` を付けない実行の `latest` で、dist-tag `latest` の版である。その版が `minimumReleaseAge` を経過していなければ、経過した版のうち最高の版に読み替えられる。`compatible` は `--compatible` を付けた実行の `latest` で、そのアプリが参照している範囲で `pnpm update` が選ぶ版である。`latest` がその範囲を満たせば `latest` になる。満たさなければ、範囲を満たす成熟した版のうち最高の版になる。その版が deprecated なら、deprecated でない版のうち最高の版になる。参照している範囲の意味は §6 の 5. と同じ。片方の実行にその行が無ければ、その実行から取る版は `current` と等しいとする。JSON の `wanted` は使わない。`wanted` は `pnpm-lock.yaml` の版、`current` は `node_modules/.pnpm` の lockfile の版で、`--filter` を付けない `pnpm install` の直後は必ず一致する。`pnpm outdated -r --format json` は使わない。同じパッケージが 2 つの版に解決されていると、パッケージ名をキーにした JSON は片方の行しか返さないためである。
- 対象アプリ: あるパッケージについて、候補一覧にそのパッケージの行を持ち、そのパッケージを置いていく直書きで持たないアプリ。
- 組: 候補同士で peer を要求し合うパッケージの集まり。判定は §1 の「組の判定」で行う。組の代表名は、名前の昇順で最初のパッケージ名とする。ブランチ名と Issue の題名の `<pkg>` には代表名を使う。手順で `<pkg>` を指定するコマンドには、組の全パッケージを並べて指定する。どの候補とも peer を要求し合わないパッケージは、それ 1 つで組とする。以降の手順で「1 パッケージずつ」「パッケージごと」とあるのは組ごとの意味で、昇順は代表名で取る。
- 解除候補: §1 で解除条件を満たすと判定した置いていく直書き。そのラウンドの §2 と §3 の後に、§4 の「解除」で `"catalog:"` に戻す。
- 合格 / 不合格: §6 の全項目を満たすか否か。

## 前提

- pnpm 10.20.0 以上を使う。この文書が前提にする動作は次の版で入った。`pnpm update` が catalog のエントリを書き換える (10.12.1)。`minimumReleaseAge` (10.16.0)。`pnpm outdated` が `minimumReleaseAge` を尊重する (10.18.0)。`minimumReleaseAgeExclude` に `<pkg>@<version>` を書ける (10.19.0)。dist-tag `latest` の版が `minimumReleaseAge` を経過していないとき、経過した版のうち最高の版に読み替える (10.20.0)。pnpm 10 系では、全版が `minimumReleaseAge` より新しいパッケージがあると `pnpm outdated` が `ERR_PNPM_NO_MATCHING_VERSION` で失敗する。pnpm 11 で修正されている。
- pnpm 10.31.0 未満では、pnpm が `pnpm-workspace.yaml` を書き換えるとコメントが消え、キーが並び替わる。記録はコメントに置かず、Issue に置く。
- `minimumReleaseAge` を設定している。公開直後の版は `pnpm outdated` にも `pnpm update` にも現れない。成熟した版を 1 つも含まない範囲を書いて `pnpm install` すると `ERR_PNPM_NO_MATURE_MATCHING_VERSION` で失敗し、lockfile は書かれない。設定していない workspace では、`minimumReleaseAge` に触れる項目を読み飛ばす。
- `pnpm-workspace.yaml` に `catalogs:` を置かない。`catalogMode` は既定の `manual` のままにする。`strictPeerDependencies` は既定の `false` のままにする。`true` にすると peer の不一致で `pnpm install` が失敗し、§6 の 4. の判定に進めない。
- 全アプリの package.json に `typecheck`、`test`、`build` のスクリプトがある。コードを生成するアプリは `generate` スクリプトを持つ。
- §3 の 5. で使う修正試行の上限は、作業時間で決める。上限の値はチームで一度決めてこの文書に書く。決めるまでは 1 アプリにつき 4 時間とする。
- 判断の記録は Issue に置く。題名は次の固定形式にする。
  - 見送り: `deps: <pkg> <version> を見送り`
  - 置いていく直書き: `deps: <app> の <pkg> を <値> に留める`
  - ベースライン不合格: `deps: ベースライン不合格 <app>`
  - `minimumReleaseAgeExclude` の追加: `deps: 例外 <pkg>@<version>`
  - 実行の中断: `deps: 実行失敗 <YYYY-MM-DD>`

## 判断の早見表

| 状況 | やること | 節 |
|---|---|---|
| 候補に範囲内更新がある | 全アプリ一括で `pnpm update -r` | 2 |
| 候補にメジャー更新がある | §2 の PR を merge した後、1 パッケージずつ全アプリで試し、結果で分類する | 3 |
| 更新で一部のアプリだけ不合格 | 不合格アプリごとに §3 の 5. で判定する。置いていくアプリの package.json を置いていく直書きにし、共有 catalog は新版にする | 3, 4 |
| メジャー更新で対象アプリが全部不合格 | 見送る。Issue に記録する。次回また候補に出る | 3 |
| peer の警告だけ出て typecheck、test、build は合格 | §6 の 9. で警告の組を `peerDependencyRules.allowedVersions` に記録して合格にする | 6 |
| 欲しい版が `minimumReleaseAge` で出てこない | 待つ。severity high 以上の脆弱性対応のときだけ `minimumReleaseAgeExclude` に版を書く | 3 |
| 置いていく直書きの解除条件を満たした | そのラウンドの §2 と §3 の PR を merge した後に、単独の PR で解除する | 4 |
| 更新前から不合格のアプリがある | Issue に記録して検証対象から外し、更新は始める。そのアプリは共有 catalog に従わせる | 1 |

## 1. 更新開始前に確認すること

各行の合格条件を満たしてから始める。満たさない行は「満たさないとき」の列に従う。直す作業は、§2 のブランチの先頭に 1 行 1 コミットで入れ、§2 と同じ PR に含める。自動実行が行ってよいのは、`pnpm install`、例外の期限の行の削除、差分の無い `pnpm dedupe` の 3 つだけで、それ以外の行で満たさないときは中断する。

| 確認 | 合格条件 | 満たさないとき |
|---|---|---|
| 作業ツリー | `git status --porcelain` の出力が空 | commit するか stash する。自動実行なら中断する |
| pnpm の版 | `pnpm --version` がルート package.json の `packageManager` の版と一致する | 別コミットで pnpm を上げてから始める。自動実行なら中断する |
| スクリプト | 全アプリの package.json に `typecheck`、`test`、`build` がある | 無いアプリに追加する別コミットを先に入れる |
| lockfile の整合 | `pnpm install --frozen-lockfile` の終了コードが 0、かつ `pnpm dedupe --check` の終了コードが 0 | `pnpm install --frozen-lockfile` が非 0 なら `pnpm install` を実行し、lockfile だけを単独で commit する。`pnpm dedupe --check` が非 0 なら、先に HEAD の lockfile のまま「ベースラインの検証」と「peer 警告の基準」の行を済ませてから `pnpm dedupe` を実行する。`pnpm install` ではこの状態は直らない。lockfile の差分で解決版が上がったパッケージを列挙する。列挙が空なら lockfile だけを単独で commit する。空でなければ、検証していない解決版の変更である。§7 の `pnpm --filter <app> update <pkg>` が commit された場合のほか、推移的依存の重複解消でも起きる。その lockfile で §6 を全アプリで実行し、合格なら 1 コミットにしてメッセージに上がった全パッケージと版を列挙する。ベースラインで合格したアプリが不合格になったときは、上がったパッケージが共有 catalog にあり、かつその不合格アプリの package.json にそのパッケージの `"catalog:"` の行があれば §3 の 5. で判定し、置いていくなら §4 に従う。このとき §4 の 2. の値は、差分の旧版と新版のメジャーが同じなら固定版 `<旧版>`、異なれば `^<旧版>` とする。§4 の 6. の `unblock:` は、前者なら `<pkg>@><新版>`、後者なら §3 の 5. の判定に従って書く。上がったパッケージが共有 catalog に無いか、その不合格アプリがそのパッケージを推移的にしか持たず `"catalog:"` の行を持たない場合は、§4 の 2. と 5. に書き換える行が無いので §4 は使えない。人が原因のアプリの Issue に記録し、対応を決めるまで差分は commit しない |
| ベースラインの検証 | 全アプリで `generate`（あれば）、`typecheck`、`test`、`build` が合格する。実行方法は §6 の 6. と 7. | 不合格のアプリごとに Issue `deps: ベースライン不合格 <app>` を作る。そのアプリは今回の §6 の 6. と 7. から `--filter '!<app>'` で外す。更新は始める |
| peer 警告の基準 | `pnpm install --resolution-only` の出力から `unmet peer` を含む行を保存した | なし |
| 例外の期限 | `minimumReleaseAgeExclude` に、公開から `minimumReleaseAge` 分を経過した版が残っていない。公開時刻は `pnpm view <pkg> time --json` で見る | 経過した行を消し、単独で commit する。対応する Issue `deps: 例外 <pkg>@<version>` を close する |
| 候補一覧 | 全アプリで `pnpm --filter <app> outdated --format json` と `pnpm --filter <app> outdated --compatible --format json` を実行し、どちらも標準出力が JSON として読め、標準エラーに `ERR_PNPM_` を含む行が無く、連結した出力を保存した。終了コードは候補があると 1 になるので合否に使わない | `ERR_PNPM_NO_MATCHING_VERSION` で失敗したときは `minimumReleaseAgeExclude` を使わない。エラーに出たパッケージ名と、その最古の版が公開から `minimumReleaseAge` を経過する時刻を Issue `deps: 実行失敗 <YYYY-MM-DD>` に書き、その時刻まで更新を始めない。公開時刻は `pnpm view <pkg> time --json` で見る。人が行うときも自動実行と同じ扱いにする |
| 置いていく直書きの一覧確認 | 全アプリの package.json の `dependencies` と `devDependencies` で、共有 catalog にあるパッケージを `"catalog:"` 以外で書いている行をすべて列挙した。列挙のコマンド例は表の下。各行に対応する open な Issue があり、値が 2 形式のどちらかである。対応するとは、題名の `<app>` がそのアプリで、題名の `<pkg>` がその行のパッケージか、本文の `keep:` 行にその行のパッケージ名があること。題名の `<値>` と `keep:` 行の値は照合しない。`^<旧メジャーの版>` の形は `pnpm update -r` で範囲内に書き換わるので、値は Issue を作った時点から動く | 先に Issue の有無を見る。Issue が無い行は、その値の最小版のメジャーを共有 catalog の範囲の最小版のメジャーと比べる。低いか等しければ解除候補にする。ただし同じメジャーなら解除候補にせず、その行を `"catalog:"` に戻して §2 の PR に含める。高ければ解除候補にせず、そのパッケージを今回の §3 のメジャー候補に加える。候補一覧にそのパッケージの行が無ければ §3 には加えず、同じく `"catalog:"` に戻して §2 の PR に含める。§3 に加えた場合、§3 の 2. のコマンドを実行する前にその行を `"catalog:"` に戻す。戻した後は置いていく直書きを持たないので、§3 の 1. では対象アプリに数え、§3 の 2. は「持つアプリが無い場合」の手順で進める。そのアプリが §3 の 4. で不合格になり 5. で置いていくと判定したときは、§4 の 2. の値を `^<戻す前の行のメジャー>.0.0` とする。§3 が見送りになった場合は、その行を直書きのまま残し、見送りの Issue に「<app> が <値> で先行している。全アプリを上げるか、<app> を共有 catalog の版に下げるかを人が決める」と書く。決めるまでは毎ラウンド同じ扱いになる。Issue がある行のうち値が 2 形式でないものは、Issue の理由が §3 の 5. の 2. か 3. なら `^<旧メジャーの版>` に、範囲内更新で置いたなら固定版に直して単独で commit する |
| 解除条件の判定 | Issue のある置いていく直書きごとに、Issue の各 `unblock:` 行の条件を `pnpm view <パッケージ> versions --json` と `pnpm view <パッケージ> time --json` で判定した。1 行の条件は、それを満たす版のうち公開から `minimumReleaseAge` 分を経過した版が 1 つでもあれば満たす。`unblock:` 行が複数ある Issue は、全行を満たしたときだけ満たす | 満たすものは解除候補にする。`unblock:` 行が無い Issue は人が判定する。自動実行では「未判定」として PR 本文に列挙する |

候補の区分は候補一覧で判定する。いずれかのアプリで `compatible` が `current` より高ければ範囲内更新あり。いずれかのアプリで `latest` が `compatible` より高ければメジャー更新あり。1 つのパッケージが両方に当てはまることがある。範囲の中に新しい版があり、範囲の外にさらに新しいメジャーがある場合である。アプリの範囲が dist-tag `latest` より上にあるパッケージは、`--compatible` を付けない実行に行が無く、`latest` を `current` と等しく取る。比較を「異なれば」にすると、そのパッケージをメジャー更新ありと誤判定する。対象アプリが 1 つも無いパッケージもメジャー候補にする。その場合 §3 は共有 catalog の行だけを上げ、§3 の 4. では不合格アプリが無いので採用になる。両方あるパッケージは §2 を先に済ませてから §3 で扱う。

組の判定は、候補 `<pkg>` ごとに `pnpm view <pkg>@<版> peerDependencies` を実行し、出力に別の候補パッケージが含まれればその 2 つを同じ組にする。組は推移的にまとめる。判定は §2 用と §3 用に分ける。§2 用は範囲内更新ありの候補だけを対象に `<版>` を `compatible` として判定し、§3 用はメジャー更新ありの候補だけを対象に `<版>` を `latest` として判定する。片方の流れでしか動かない候補を組に入れても、その流れでは一緒に上がらないためである。§4 は来た節の組を使う。

「置いていく直書きの一覧確認」のコマンド例。`<apps>` はアプリを置くディレクトリ。`yq` は mikefarah 版 yq v4 を指す。`dependencies` と `devDependencies` だけを見て、値が `"catalog:"` と完全一致する行を除く。

```bash
for pkg in $(yq -r '.catalog | keys | .[]' pnpm-workspace.yaml); do
  node -e 'const [pkg,...files]=process.argv.slice(1);for(const f of files){const j=JSON.parse(require("fs").readFileSync(f,"utf8"));for(const k of ["dependencies","devDependencies"]){const v=j[k]&&j[k][pkg];if(v&&v!=="catalog:")console.log(`${f}: ${k}.${pkg} = ${v}`)}}' "$pkg" <apps>/*/package.json
done
```

解除候補があれば、そのラウンドの §2 と §3 の PR をすべて merge した後に §4 の「解除」を単独の PR で行う。自動実行は解除を行わず、その Issue の題名を PR 本文に列挙する。Issue の無い解除候補は、アプリ名、パッケージ名、値を同じ項に列挙する。

## 2. 通常の更新フロー（範囲内更新）

範囲内更新は、全アプリが合格する限り判断を要しない。全アプリを一括で上げる。不合格が出たときだけ 5. で人が判定する。

1. ブランチを切る。名前は `deps/range/<YYYY-MM-DD>` とする。
2. `pnpm update -r` を実行する。共有 catalog、置いていく直書き、その他の直書きのすべてが、それぞれの範囲内で最新になる。固定版の置いていく直書きは書き換わらない。ルートの package.json の直書きも同時に更新される。lockfile と node_modules も更新される。
3. 変更を次の 3 条件で検査する。1 つでも満たさなければ、`git restore --staged --worktree .` で戻し、`pnpm install --frozen-lockfile` を実行して中断する。
   - `pnpm-workspace.yaml` を YAML として読み、`catalog`、`peerDependencyRules`、`minimumReleaseAgeExclude` 以外のキーの値が更新前と等しい。キーの並びとコメントの変化は前提のとおりで、比較しない。
   - 変わった各エントリで、新しい範囲の最小版が更新前の範囲を満たす。満たさないエントリがあれば手順を誤っている。
   - package.json で変わったのは依存の範囲だけである。引数なしの `pnpm update -r` では直書きが `"catalog:"` に書き換わることは無い。5. の `pnpm update -r <pkg>` では、実行前の範囲文字列が共有 catalog のエントリと完全に同じだった直書きが `"catalog:"` に書き換わる。これは pnpm の正常な動作で、そのまま受け入れる。置いていく直書きは共有 catalog より古い版なので、同じ文字列にならない。
4. §6 の検証を全アプリで実行する。
5. 結果で分岐する。
   - 全アプリ合格: 1 コミットにする。コミットメッセージに更新したパッケージと版を列挙する。
   - 1 つでも不合格: 変更を `git restore --staged --worktree .` で戻し、`pnpm install --frozen-lockfile` を実行する。次に、§1 で範囲内更新ありと区分したパッケージを代表名の昇順で 1 つずつ `pnpm update -r <pkg>` で上げる。上げるたびに 3. の検査と §6 の検証を全アプリで実行する。直前までに合格してコミットした状態の上で次を試す。
     - 全アプリ合格のパッケージは、1 パッケージ 1 コミットで記録する。
     - 一部のアプリだけ不合格のパッケージは、変更を戻し、`pnpm install --frozen-lockfile` を実行し、パッケージ名と不合格アプリと失敗内容を記録して次のパッケージに進む。候補一覧を最後まで試してから、記録したパッケージごとに `pnpm update -r <pkg>` をもう一度実行し、不合格アプリごとに §3 の 5. で判定する。置いていくと判定したアプリがあれば §4 に従う。自動実行は、候補一覧を最後まで試し、合格してコミットした分を push して PR を開き、記録したパッケージごとにパッケージ名と不合格アプリと失敗内容を PR 本文に書き、PR を draft のままにして終了する。記録したパッケージの再実行と §3 の 5. は人が行う。
     - 対象アプリが全部不合格のパッケージは、変更を戻して見送る。Issue `deps: <pkg> <version> を見送り` に、どのアプリがどう不合格になったかを書く。
6. 見送ったパッケージは次回の候補一覧に再び現れる。設定で隠さない。
7. severity high 以上の脆弱性の修正版が `minimumReleaseAge` のために候補一覧に出てこない場合は、§3 の 6. に従う。

範囲内更新で不合格になる原因は、依存側の semver 違反か自アプリ側の潜在バグである。どちらでも扱いは同じで、§3 の 5. で判定する。

## 3. メジャー更新の判断フロー

メジャー更新は §2 の PR を merge した後に始める。パッケージごとに 1 つのブランチと 1 つの PR にする。ブランチ名は `deps/major/<pkg>-<version>` とし、`<version>` は代表名のパッケージの上げる先の版とする。候補が複数あるときは代表名の昇順で処理し、前の PR を merge してから次を始める。見送りにした候補は次の候補の開始を妨げない。見送りの Issue を書いた時点で次の候補に進む。自動実行も同じ順序に従う。

1. 対象アプリを確認する。用語のとおり、`<pkg>` を置いていく直書きで持つアプリは対象外である。対象外のアプリは §6 の 5. で置いていく直書きの範囲に留まっていることだけを確認する。§1 で検証対象から外したアプリは判定の対象にしない。そのアプリは共有 catalog に従わせ、置いていく直書きにはしない。PR 本文とそのアプリの Issue に「未検証のまま前進した」と書く。
2. まず対象アプリを全部上げてみる。判断は結果で行う。上げる先は候補一覧の `latest` とする。
   - `<pkg>` を置いていく直書きで持つアプリが無い場合: `pnpm update -r --latest <pkg>` を実行する。共有 catalog のエントリなら 1 行が書き換わって全アプリが新版に解決される。直書きなら全 package.json の行が書き換わる。実行後に、書き込まれた版が候補一覧の `latest` と一致することを確認する。`--latest` は候補一覧の `latest` の版と、今の範囲で `pnpm update` が選ぶ版の高い方を書く。§3 の候補は `latest` が `compatible` より高いので、書き込まれる版は候補一覧の `latest` と一致する。一致しなければ候補一覧が古い。変更を戻し、§1 からやり直す。
   - `<pkg>` を置いていく直書きで持つアプリがある場合: `pnpm update -r --latest <pkg>` はその直書きも新版に書き換える。代わりに共有 catalog の行を `^<latest>` に手で書き換え、`pnpm install` を実行する。置いていく直書きには触れない。
   - `latest` より低いメジャーへ上げるのは、同じ実行で `latest` への更新が 4. で全部不合格になり見送りの Issue を作るかコメントを追記した直後に、別の PR で 1 つ低いメジャーを試す場合だけとする。試すのは 1 段だけで、それも全部不合格なら同じ Issue に「`<major>.0.0` も見送り」とコメントし、4. の表のとおり移行を計画する。移行を計画する Issue が open の間は、1 段低いメジャーを試さない。前回以前の見送り Issue が open でも、人が行うときは `latest` から試し、同じ版で再び全部不合格なら §8 のとおりその Issue にコメントを追記する。共有 catalog の行を `^<major>.0.0` に手で書き換えて `pnpm install` する。`<pkg>` が共有 catalog に無ければ、`<pkg>` を持つ全アプリの package.json の行を `^<major>.0.0` に手で書き換える。解決される版は pnpm が `minimumReleaseAge` を満たす範囲で選ぶ。`ERR_PNPM_NO_MATURE_MATCHING_VERSION` で失敗したら、そのメジャーにはまだ取り込める版が無い。変更を戻して見送る。`<major>` が 0 のときは試さない。ブランチ名の `<version>` と、全部不合格のときの見送り Issue の題名の `<version>` は `<major>.0.0` とする。§6 の 5. の「上げる先の版」は解決された版とする。`<pkg>@<major>` の形は対象アプリの `"catalog:"` を直書きに変えるので使わない。
3. §6 の検証を全アプリで実行する。
4. 結果を分類する。上から順に最初に該当した行を採る。分類に数えるアプリは 1. の対象アプリとする。対象アプリに含まれないアプリが不合格になった場合も、不合格アプリとして 5. の判定に回す。§1 で検証対象から外したアプリは §6 の 7. を実行していないので、ここには現れない。

| 結果 | 対応 |
|---|---|
| 不合格アプリが 1 つも無い | 採用する。1 コミット |
| 対象アプリが全部不合格 | 5. の判定をせずに見送る。変更を戻し、Issue `deps: <pkg> <version> を見送り` に不合格の内容を書く。見送った版が `latest` で、`latest` のメジャーより 1 つ低いメジャーが、共有 catalog にあればその行の現在の範囲、無ければ更新前の package.json の範囲、の最小版のメジャーより高ければ、次にそのメジャーを 2. の手順で別の PR として試す。それ以外は、全アプリの移行を別の作業として Issue で計画し、その作業の PR に `latest` へのメジャー更新を含める |
| 上のどちらでもない | 不合格アプリごとに 5. の判定をする。置いていくアプリがあれば §4 で置いていく直書きにする |

5. 不合格アプリごとに、次の順で判定する。最初に当てはまったものを採る。この判定は人が行う。自動実行では、不合格アプリと失敗内容を PR 本文に列挙するところまでにする。不合格アプリに §6 の 4. の新しい `unmet peer` 行があり、その行の peer 名が `<pkg>` なら、1. を飛ばして 2. とする。無ければ 1. から判定する。
   1. 落ちた原因が、そのアプリ自身のコード変更だけで解消できる可能性がある。修正を試みる。試行の上限は前提に書いた作業時間とする。上限内に §6 が合格すれば、修正を含めて前進させる。合格しなければ修正を戻し、2. か 3. に進む。依存の追加、削除、差し替えを伴う修正はここに当てはめない。それらは 2. とする。
   2. 落ちた原因が、そのアプリが使う別の依存の未対応である。peer の範囲、対応版が未公開、エンジン要件、依存の差し替えが必要、がこれにあたる。置いていく。§4 へ。
   3. 上のどちらにも当てはまらない。原因不明や大規模な書き換えがこれにあたる。置いていく。§4 へ。原因調査は Issue で別に行う。
6. `minimumReleaseAgeExclude` を書いてよいのは、脆弱性対応のときだけとする。他のどの手順でも書かない。候補一覧が `ERR_PNPM_NO_MATCHING_VERSION` で取れない場合も書かず、§1 のとおり待つ。脆弱性対応とは、`pnpm audit` が今の解決版に severity high 以上の advisory を報告し、その修正版が公開から `minimumReleaseAge` を経過していない場合を指す。moderate 以下は待つ。該当する場合は `minimumReleaseAgeExclude` に `<pkg>@<version>` を書いて取り込む。追加は人が行い、Issue `deps: 例外 <pkg>@<version>` に根拠の advisory を書く。その行は §1 の「例外の期限」で消し、同時にその Issue を close する。

## 4. 一部アプリだけ更新できない場合の扱い

§1 の「lockfile の整合」、§2、§3、または §5 で「置いていく」と判定したアプリがある状態から始める。

原則:

- 共有 catalog は前進後の版にする。新しいアプリは共有 catalog を参照する。
- 置いていくアプリは、そのアプリの package.json を置いていく直書きにする。置いていく直書きには Issue で理由と解除条件を付け、解除条件を満たしたら「解除」で `"catalog:"` に戻す。
- 共有 catalog の版は置いていく直書きの版より常に新しくする。置いていくアプリの方が多くてもこの関係を保つ。
- 置いていくアプリの範囲内更新は止めない。`^<旧メジャーの版>` の形なら `pnpm update -r` の対象に含まれ続ける。固定版の形は書き換わらない。
- 同じパッケージを別の版で置いていくアプリが複数あってよい。アプリとパッケージごとに別の Issue を持つ。

手順:

1. 共有 catalog の `<pkg>` を新しい範囲にする。§2 の 5. の `pnpm update -r <pkg>` か §3 の 2. で済んでいれば何もしない。§5 から来た場合と、§1 の「lockfile の整合」から来た場合も何もしない。
2. 置いていくアプリの package.json で、`<pkg>` の `"catalog:"` を置いていく直書きに変える。
   - メジャー更新で置いていくなら、値は更新前の共有 catalog の範囲をそのまま書く。例: `"^1.4.0"`。
   - 範囲内更新で置いていくなら、値は候補一覧の `current` の値を `"1.2.3"` のように固定で書く。上限付きの範囲は書かない。`pnpm update -r` が上限付きの範囲を `^<解決版>` に書き換えて上限を失うためである。
   - §5 から来た場合は、値を `^<そのアプリが使うメジャー>.0.0` とする。
   - 組で置いていく場合は、組の全パッケージを同じ形で書く。
   - 置いていくアプリが複数あれば、各アプリの package.json に同じ値を書く。
   - 既に `^<旧メジャーの版>` の形で置いている行を、範囲内更新の不合格でさらに置いていくときは、その行を固定版に書き換え、既存の Issue の題名の `<値>` を固定版に変える。`unblock:` 行は変えず、新しい Issue も作らない。そのアプリは解除まで範囲内更新を受けない。
3. `pnpm install` を実行する。
4. 出力の `unmet peer` 警告のうち、置いていくアプリに出て、peer 名が `<pkg>` であるものを集める。警告を出したパッケージが、そのアプリの package.json に `"catalog:"` で書かれていて、この PR のベースコミットと比べてそのアプリでの解決版が上がっていれば、そのパッケージも同じ形で置いていく直書きにする。値は 2. の規則に従う。推移的依存の警告はここでは扱わず、5. に回す。該当が無くなるまで 3. と 4. を繰り返す。
5. §6 の検証を全アプリで実行する。4. で扱わなかった警告や、警告が無い不合格で置いていくアプリが不合格になった場合は、原因のパッケージを人が指定し、そのパッケージを 2. の規則で置いていく直書きにして 3. からやり直す。指定できるのは、そのアプリの package.json に `"catalog:"` で書かれたパッケージに限る。
6. 置いていくアプリごとに Issue `deps: <app> の <pkg> を <値> に留める` を作り、次を書く。
   - 留めた版、留めた理由。理由は §3 の 5. の 2. か 3. のどちらか。組の他のパッケージと、4. で追加した置いていく直書きは、`keep: <パッケージ>@<留めた時点の値>` の行で 1 つずつ列挙する。照合はパッケージ名で行う。
   - 解除条件。機械で判定できる形は `unblock: <パッケージ>@<範囲>` の行で書く。意味は「そのパッケージにその範囲を満たす版が公開されたら解除を試す」。`<依存>` はそのアプリの package.json に書かれた直接依存に限る。推移的依存が原因なら、それを引き込む直接依存を書く。§3 の 5. の 2. で置いた場合は、未対応の依存ごとに `unblock: <依存>@><そのアプリで今回解決された版>` と書く。解決された版は `pnpm ls -r <依存> --depth 0 --json` で取る。固定版で置いた場合は `unblock: <pkg>@><候補一覧の compatible>` の 1 行だけを書く。`compatible` は範囲内更新で入ってきた壊れた版である。§3 の 5. の 3. で置いた場合は `unblock:` 行を置かない。機械で判定できない条件は文章で書く。
7. 共有 catalog の変更と、置いていくアプリの package.json の変更は、1 コミットに入れる。分けると、間のコミットで共有 catalog が新版なのに置いていくアプリが旧版に留まる理由を持たない状態になる。

解除:

解除は、そのラウンドの §2 と §3 の PR をすべて merge した後に、単独の PR で行う。ブランチ名は `deps/unblock/<YYYY-MM-DD>` とする。同名のブランチか PR が既にあれば、末尾に `-2` から始まる連番を付ける。対象は §1 で解除候補とした置いていく直書きと、脆弱性対応で解除候補に加えたもの。候補が複数あっても 1 つの PR にまとめ、PR 本文に全候補の Issue の題名を列挙する。Issue の無い候補は題名の代わりにその行、つまり package.json のパス、パッケージ名、値を書く。解除の中で依存を上げることはしない。依存はそのラウンドの §2 と §3 で上がっている。

1. 候補ごとに、試す条件を確認する。Issue の各 `unblock:` 行の依存について、解決版を `pnpm ls -r <依存> --depth 0 --json` で取る。見るアプリは、その依存を `"catalog:"` で参照しているアプリのうち任意の 1 つとする。共有 catalog 参照のアプリは同じ版に解決されるので 1 つで足りる。そのアプリが 1 つも無ければ、共有 catalog の現在の範囲を満たす版のうち公開から `minimumReleaseAge` 分を経過した最高版を `pnpm view <依存> versions --json` と `pnpm view <依存> time --json` で取り、それを解決版として比べる。その依存が共有 catalog に無ければ、候補のアプリの解決版を見る。全行で解決版が `unblock:` の範囲を満たせば試す。1 行でも満たさなければ、その候補は今回の解除から外し、PR 本文に依存名と解決版を書く。Issue の無い候補と、脆弱性対応で加えた候補は、この確認を行わない。同じアプリの複数の Issue が同時に候補なら、それらの行はまとめて戻し、まとめて検証する。
2. 候補ごとに、Issue の題名の `<pkg>` と `keep:` 行のパッケージについて、置いていくアプリの package.json の置いていく直書きを `"catalog:"` に戻す。Issue の無い候補はその行だけを戻す。同じアプリの、候補でない Issue に属する行には触れない。
3. `pnpm install` を実行する。
4. §6 の検証を全アプリで実行する。判定は候補のアプリごとに行う。
   - 合格したアプリは戻したままにする。そのアプリのその Issue に属する置いていく直書きが無くなったら Issue を close する。
   - 不合格のアプリは、戻した状態でそのアプリに解決されていた版を `pnpm ls -r <pkg> --depth 0 --json` で控えてから、戻しを取り消し、`pnpm install` を実行し、§6 を全アプリでもう一度実行する。この再実行は不合格時の「もう 1 回」に数えない。再実行で合格したら、§3 の 5. で再判定する。§3 の 5. の 1. に当たり修正が上限内に合格したら、修正を含めて戻しをやり直し、`pnpm install` と §6 を再実行し、合格なら戻したままにする。それ以外は置いていくままにし、Issue に今回の不合格内容を追記する。Issue が無かった候補は Issue `deps: <app> の <pkg> を <値> に留める` を新たに作り、`<値>` は行の値とする。どちらも `unblock:` 行は §4 の 6. の規則で書き直す。版には控えておいた「戻した状態で解決されていた版」を使い、既存の行はその依存の行だけ書き換える。再実行でも不合格なら、戻しの取り消しでは直らない不合格であり、原因は解除以外にある。PR を close し、人が原因を調べて Issue `deps: 実行失敗 <YYYY-MM-DD>` に書く。
   - 候補のアプリが 1 つも合格しなかった場合は PR を close する。

置いていったアプリが severity high 以上の脆弱性対応を必要とする場合、次の順で最初に当てはまるものを採る。修正版とは、`pnpm audit` が報告する patched_versions を満たす版のうち、そのアプリの今の解決版以上で最小のものを指す。

- `^<旧メジャーの版>` の形で、修正版がその範囲内にある: §2 で済む。
- 固定版の形で、修正版が共有 catalog の現在の範囲の最小版より低い: 修正版が公開から `minimumReleaseAge` を経過していなければ、先に §3 の 6. に従って `minimumReleaseAgeExclude` に `<pkg>@<修正版>` を書く。固定版を修正版に書き換えて `pnpm install` し、§6 を全アプリで実行する。ブランチは `deps/vuln/<app>-<pkg>-<YYYY-MM-DD>` とし、単独の PR にする。合格なら 1 コミットにし、Issue の題名の `<値>` を修正版に変え、本文に advisory の ID を書く。不合格なら次の項に進む。修正版が共有 catalog の最小版以上なら次の項に進む。
- それ以外、または上の項で不合格: そのアプリを前進させる作業を最優先にする。修正版のメジャーが共有 catalog のメジャーと同じなら、§3 の 6. の例外を書いて §2 を行う。修正版のメジャーが共有 catalog より新しければ、そのパッケージについて §3 を実行する。どちらでも、そのアプリを `unblock:` の判定を省いて解除候補に加え、「解除」を行う。この解除は脆弱性対応の §2 または §3 の PR を merge した直後に行い、同じラウンドの他の §3 候補を待たない。「解除」で不合格なら、§3 の 5. の判定を人が行い、§3 の 5. の 1. の時間の上限は適用しない。§3 の 5. の 2. か 3. に当てはまるときは、依存の差し替えを含めた前進の計画を人が決めてそのアプリの Issue に書く。前進できるまでの間、同じ Issue に advisory の ID と影響範囲を書く。

## 5. 共有 catalog / named catalog / 直書きの使い分け

判断表。上から順に当てはめ、最初に該当した行に従う。

| 状況 | 置き場所 |
|---|---|
| §2、§3、§5 で「置いていく」と判定したアプリの、そのパッケージ | そのアプリだけ置いていく直書き。共有 catalog は新版 |
| 新しいアプリの雛形が package.json に書く依存 | 共有 catalog。使うアプリが 1 つでも |
| 2 つ以上のアプリが使う依存 | 共有 catalog |
| 1 つのアプリしか使わず、雛形にも無い依存 | 直書き |

共有 catalog にあるパッケージを直書きしてよいのは、置いていく場合だけである。それ以外の直書きは §1 の「置いていく直書きの一覧確認」で Issue の無い行として検出され、§1 の規則で解除候補か §3 の候補になる。

named catalog は使わない。置いていくアプリを named catalog で表しても、実測した範囲では置いていく直書きと結果が同じだった。実測したのは `pnpm update -r <pkg>`、`pnpm --filter <置いていくapp> update <pkg>`、`pnpm --filter '!<置いていくapp>' update --latest <pkg>`、`pnpm update -r --latest <pkg>` の 4 つと、上限付き範囲が `^<解決版>` に書き換わる挙動である。違いは解除のときで、named catalog は `pnpm-workspace.yaml` に参照の無いエントリが残り、それを消す設定か手順が別に要る。置いていく理由はそのアプリの事情なので、記録もそのアプリの package.json と Issue に置く。pnpm の文書は named catalog を段階的な移行に使う例を挙げている。この文書はその用法を採らない。

依存を追加するとき:

- 1 アプリだけで使い、雛形に無い: `pnpm --filter <app> add <pkg>`。版は指定しない。共有 catalog に同名があれば pnpm が `"catalog:"` を書く。無ければ直書きになる。
- 2 つ以上で使う、または雛形にある: `pnpm --filter <app> add <pkg> --save-catalog`。共有 catalog にエントリが増える。
- 直書きの依存を 2 つ目のアプリが使い始めた: 共有 catalog に移す。移す作業は、その依存を追加する PR の中で行う。
- 追加先のアプリが共有 catalog より新しいメジャーを必要とする: 先に §3 でそのパッケージを全アプリで上げる PR を出し、merge 後に追加する。§3 で一部のアプリを置いていく結果になっても、共有 catalog は新版になるので追加できる。§3 が全部不合格で見送りになった場合は、そのアプリはそのメジャーを使えない。共有 catalog の版で実装するか、依存の追加を取りやめるかは人が決め、見送りの Issue に書く。
- 追加先のアプリが共有 catalog より古いメジャーしか使えない: §3 の 5. の 2. と同じ扱いにし、§4 の手順で置いていく直書きにする。

## 6. 更新後の検証

順に実行し、すべて合格で「合格」とする。1 つでも不合格なら、呼び出し元の手順に戻り、その手順の不合格の分岐に従う。
各検証は 1 回実行する。不合格なら同じコマンドをもう 1 回だけ実行する。2 回目も不合格なら不合格とする。2 回目で合格なら合格とし、§8 の一覧に従って PR 本文に再実行した検証名を書く。
対象は全アプリとする。変更のあったアプリだけに絞らない。catalog の変更はアプリのディレクトリに触れないため、変更検知に基づくフックや CI の絞り込みは動かない。§1 でベースライン不合格だったアプリだけを 6. と 7. から外し、その旨を PR に書く。

| 順 | 検証 | 合格条件 |
|---|---|---|
| 1 | `pnpm dedupe --check` | 終了コード 0。非 0 なら `pnpm dedupe` を実行し、その差分も同じコミットに入れてから 2. に進む。共有 catalog の行だけ変わって他アプリが旧版のままの lockfile は、ここで検出される |
| 2 | `pnpm install --frozen-lockfile` | 終了コード 0 |
| 3 | `pnpm-workspace.yaml` の差分 | 更新前と作業ツリーの両方を YAML として読み、`catalog`、`peerDependencyRules`、`minimumReleaseAgeExclude` を除いた内容が等しく、`catalogs` キーが無い。`minimumReleaseAgeExclude` の差分は、この PR で §3 の 6. の手順で書いた行に限る。`peerDependencyRules` の差分は、この PR で 9. の手順で書いた行に限り、9. を行う前の実行では差分が無いこと。コマンド例は表の下 |
| 4 | peer 警告 | `pnpm install --resolution-only` の出力の `unmet peer` 行が、§1 で保存した集合の部分集合である。新しい行があれば §8 の一覧に従って PR 本文に列挙し、この時点では合否を決めずに 5. に進む |
| 5 | `pnpm ls -r <pkg> --depth 0 --json` | 各アプリの `<pkg>` の `version` が、そのアプリが今参照している範囲を満たす。参照している範囲とは、`"catalog:"` なら共有 catalog の現在の値、直書きならその値である。加えて §3 と §4 では、前進するアプリは `version` のメジャーが上げる先の版のメジャーに等しい |
| 6 | `pnpm -r --if-present run generate` | 終了コード 0。生成結果の差分は同じコミットに入れる。更新内容で実行の要否を判断しない。§1 で外したアプリは `--filter '!<app>'` で除く |
| 7 | アプリごとに `pnpm --filter <app> run typecheck`、同じく `test`、`build` | 各アプリで終了コード 0。1 つが不合格でも残りのアプリを最後まで実行し、不合格のアプリ名を列挙する。全アプリを 1 回で走らせるときは `pnpm -r --no-bail run <script>` を使い、合否は全体の終了コードではなくアプリごとの出力で読む。§1 で外したアプリは `--filter '!<app>'` で除く |
| 8 | ルートの依存 | ルートの package.json に差分があれば、それを使うルートのスクリプトやフックを 1 回実行して成功する |
| 9 | peer 警告の記入 | 4. で新しい行があり、7. が全アプリ合格のとき、`pnpm-workspace.yaml` の `peerDependencyRules.allowedVersions` に `"<警告を出した依存>><peer 名>": "<実際に解決されたメジャー>"` の形で 1 組ずつ書く。`"*"` や範囲は書かない。書いた後に `pnpm install --resolution-only` をもう一度実行し、新しい行が無ければ合格。書いた後は 2. と 3. だけをもう一度実行する。この再実行は不合格時の「もう 1 回」に数えず、§8 の再実行一覧にも書かない。2. が非 0 なら `pnpm install` を実行し、lockfile の差分を同じコミットに入れて 2. をもう一度実行する。7. に不合格のアプリがあれば記入せず、その警告は §3 の 5. と §4 の手順の 4. の判定に使う。この記入は人が行う |

検証 3. のコマンド例。`<base>` は更新前のコミット。`yq` は mikefarah 版 yq v4 を指す。

```bash
diff <(git show <base>:pnpm-workspace.yaml | yq -o json 'del(.catalog, .peerDependencyRules, .minimumReleaseAgeExclude)') <(yq -o json 'del(.catalog, .peerDependencyRules, .minimumReleaseAgeExclude)' pnpm-workspace.yaml)
```

## 7. やってはいけない操作

| 操作 | 何が起きるか | 代わりに |
|---|---|---|
| `pnpm update -r --latest` をパッケージ指定なしで実行する。否定パターンで一部を除いた場合も禁止する | 除外しなかったパッケージは置いていく直書きも最新メジャーに書き換わり、そのパッケージで置いていったアプリも新版になる。複数のメジャー更新が混ざり、不合格の原因を切り分けられない | メジャー更新は §3 で 1 パッケージずつ |
| `pnpm --filter <app> update <pkg>` で共有 catalog の依存を「そのアプリだけ」上げる | 共有 catalog の行は新版に書き換わるが、再解決されるのは指定したアプリだけになる。他アプリは lockfile 上で旧版のまま残り、lockfile の `catalogs.default` は specifier が新版で version が旧版という不整合になる。`pnpm install --frozen-lockfile` はこの状態を通し、その後の `pnpm install` でも直らない。`pnpm dedupe --check` が非 0 になり、`pnpm dedupe` で全アプリが新版に揃う | 共有 catalog の依存は `pnpm update -r <pkg>` で全アプリ一括で扱う。分けるなら §4。commit 済みなら §1 の「lockfile の整合」で復旧する |
| `pnpm update <pkg>@<version>` や `<pkg>@<major>` のようにバージョン付きで実行する。`-r` でも `--filter` でも同じ | 対象アプリの `"catalog:"` が直書きに書き換わり、Issue の無い置いていく直書きができる。`-r` なら全アプリで起きる | 特定のメジャーへ上げるときは共有 catalog の行を手で書き換えて `pnpm install` する。§3 の 2. |
| 共有 catalog にあるパッケージを、置いていく目的以外で直書きする | 範囲文字列が共有 catalog と完全に同じなら、`pnpm update -r <pkg>` か `pnpm update -r --latest` で `"catalog:"` に書き換えられる。固定版 `1.2.3` と共有 catalog `^1.2.3` のように解決版が同じでも文字列が違えば書き換えられない。違う文字列の行は §1 の一覧確認で Issue の無い行として解除候補か §3 の候補になる | `"catalog:"` を書く。置いていくなら §4 |
| 置いていく直書きを上限付きの範囲で書く | `pnpm update -r` が `^<解決版>` に書き換えて上限を失う | `^<旧メジャーの版>` か固定版 `x.y.z` |
| named catalog で置いていく | 実測した範囲では置いていく直書きと同じ挙動で、解除後に `pnpm-workspace.yaml` に参照の無いエントリが残る | §4 の置いていく直書き |
| `overrides` でアプリ別に固定する | package.json に現れず、次の担当者が気づけない | §4 の置いていく直書き |
| `updateConfig.ignoreDependencies` で置いていく | 全アプリに効く。公式ドキュメントでは `pnpm outdated` からも消える。pnpm 10 では root の package.json に書かないと update に効かず、pnpm 11 でその置き場所が廃止される | Issue で追跡する。次回の候補一覧に再び現れたら §2 と §3 で通常どおり試す |
| `pnpm-workspace.yaml` だけ変えて lockfile を更新せずに commit する | CI の `--frozen-lockfile` で落ちる | `pnpm install` を実行して lockfile も commit |
| lockfile を手で編集する | 整合が壊れる | conflict は §8 の手順で解消する |
| 検証を変更検知に任せる | catalog 変更ではフックが走らない | §6 を全アプリで実行 |
| `minimumReleaseAge` を下げて最新を取る | 全パッケージで公開直後の版が候補に入る | `minimumReleaseAgeExclude` に `<pkg>@<version>` を書く。§3 の 6. |
| 成熟した版を 1 つも含まない範囲を書く | `pnpm install` が `ERR_PNPM_NO_MATURE_MATCHING_VERSION` で失敗する。lockfile は書かれない | 候補一覧の `latest` か `^<major>.0.0` を書く。§3 の 2. |
| pnpm 自体の更新を依存更新と同じコミットに入れる | 不合格のときに原因を切り分けられない | pnpm の更新は単独コミット |

## 8. CI / 自動化するときの考慮事項

- CI の install は `pnpm install --frozen-lockfile` にする。`pnpm dedupe --check` も CI のゲートに入れる。`--frozen-lockfile` だけでは、共有 catalog の行と他アプリの解決版がずれた lockfile を通してしまう。
- 自動実行が自分で commit と PR 作成をしてよいのは、§2 と、§3 の候補のうち代表名の昇順で最初の 1 つまでとする。§3 では「全アプリで試し、§6 の結果をアプリ別に報告する」までを行い、PR は draft で開く。次の候補の PR は、前の PR が merge された後の実行で開く。§3 の 5. の判定、§4、§6 の 9. の記入は人が行う。PR の merge は人が行う。自動実行が §6 の 4. で新しい `unmet peer` 行を見つけたときは、その行を PR 本文に列挙して §6 の 5. 以降を続け、PR を draft のままにする。
- 自動実行が `--latest` を使うのは §3 の 2. の `pnpm update -r --latest <pkg>` だけとする。`<pkg>` を置いていく直書きで持つアプリがある場合は手順が手作業になるため、自動実行はそのパッケージを対象から外して PR 本文に列挙し、外したパッケージを飛ばした昇順で最初の候補を扱う。外したパッケージの PR は人が開き、自動実行はその merge を待たない。open な見送り Issue があるパッケージも同じく外し、再試行は人が行う。
- ブランチと PR は §2 が `deps/range/<YYYY-MM-DD>` で 1 本、§3 が候補ごとに `deps/major/<pkg>-<version>` で 1 本の draft PR とする。
- PR 本文に書く項目は次のとおりとする。候補一覧の各エントリのアプリ名、`package`、`current`、`compatible`、`latest`。実行時刻 (UTC)。`pnpm --version`。`minimumReleaseAge` の値。§1 で外したアプリ。未判定の Issue。置いていく直書きがあるため §3 の対象から外したパッケージ。§6 で再実行した検証名。§6 の 4. で新しく出た `unmet peer` 行。§6 の 7. で不合格になったアプリ名と失敗内容。§2 の 5. で一部のアプリだけ不合格になったパッケージ名と不合格アプリと失敗内容。§1 で解除候補としたが自動実行では解除しなかった Issue の題名と、Issue の無い解除候補のアプリ名、パッケージ名、値。§1 の「満たさないとき」で自動実行が中断した行。他の節の「PR 本文に書く」はこの一覧を指す。
- Issue を作る前に同じ題名の open な Issue を検索する。あればコメントを追記し、無ければ新規に作る。
- 各実行は既定ブランチの最新 commit から新しい作業コピーで始める。前回の作業ツリーを再利用しない。同じ名前のブランチか PR が既に open なら、その実行は何もせず終了し、open の PR に「今回はスキップした」とコメントする。同時に 2 つの実行を走らせない。CI の concurrency group で直列化する。
- 手順のコマンドが合否条件以外の理由で止まったら、それまでの commit を push せず終了する。§6 の不合格はこれに含めない。失敗した手順番号と出力を Issue `deps: 実行失敗 <YYYY-MM-DD>` に書く。`pnpm outdated` が `ERR_PNPM_NO_MATCHING_VERSION` で失敗した場合はエラー文字列で判別し、エラーに出たパッケージ名と、その最古の版が `minimumReleaseAge` を経過する時刻を同じ Issue に書く。その時刻まで再実行しない。
- §6 の検証はアプリごとに独立したジョブで実行し、アプリ別の合否を出す。変更ファイルで対象を絞らない。
- 更新 PR が複数同時に開いて lockfile が衝突したときの手順は次に固定する。先に開いた PR を先に merge する。後の PR は既定ブランチに rebase する。`pnpm-workspace.yaml` と package.json の衝突は両方の変更を残す。同じパッケージの行が衝突したときは、版が高い方を残す。その後 `pnpm install` を実行し、lockfile の差分を commit する。rebase 後に §6 を全アプリで再実行する。自動実行では、衝突が `pnpm-lock.yaml` だけなら `pnpm install` を実行して commit し、それ以外のファイルに衝突があれば中断して PR にコメントする。
- 実行周期は `minimumReleaseAge` とは独立に決める。`minimumReleaseAge` は各版が候補に入る時刻を公開から一定時間遅らせるだけで、周期を短くしても公開直後の版が候補に入ることはない。周期を長くした分だけ取り込みが遅れる。
- pnpm 10.31 未満では自動実行のたびに `pnpm-workspace.yaml` のコメントが消える。前提のとおり記録はコメントに置かないので、自動化の開始に pnpm の版の引き上げは要らない。`pnpm-workspace.yaml` にコメントを残したい場合だけ、自動化を始める前に pnpm を 10.31 以上にする。
